# 웹 서비스 인증, 요즘은 무엇을 쓰나

인증을 직접 처음부터 구현하는 팀은 갈수록 줄고 있습니다. 대신 "어떤 방식을 쓸지"와 "어떤 도구에 위임할지"를 고르는 문제로 바뀌었습니다. 이 글은 특정 도구 하나를 깊게 파기보다, 요즘 웹 서비스 인증에서 자주 보이는 선택지와 그 흐름을 정리합니다.

---

## 큰 흐름 1 — 세션이 다시 주목받는다

몇 년 전까지는 "JWT를 클라이언트에 들고 있다가 매 요청에 실어 보낸다"는 방식이 대세처럼 여겨졌습니다. 하지만 최근에는 반대 방향의 조언이 많아졌습니다.

| | 세션(Session) | JWT(클라이언트 보관) |
|---|---|---|
| 저장 위치 | 서버(Redis 등) + `HttpOnly` 쿠키에 세션 ID만 | 클라이언트(localStorage/메모리)에 토큰 전체 |
| 즉시 무효화 | 서버에서 세션 삭제 → 즉시 로그아웃 | 만료 전까지 무효화 어려움(블랙리스트 필요) |
| XSS 노출 위험 | 낮음(`HttpOnly`라 JS로 접근 불가) | localStorage 저장 시 높음 |
| 서버 상태 | 있음(스케일아웃 시 세션 스토어 필요) | 없음(스테이트리스) |
| 적합한 상황 | 일반적인 웹 서비스, 브라우저 클라이언트 | 서버-서버 통신, 마이크로서비스 간 인증 |

정리하면, **브라우저에서 쓰는 일반적인 웹 서비스라면 `HttpOnly` 쿠키 기반 세션**이 다시 기본값으로 권장되는 추세이고, JWT는 여러 서비스가 서로를 호출하는 서버 간 통신이나 API 게이트웨이처럼 스테이트리스가 꼭 필요한 자리에 쓰는 쪽으로 역할이 좁혀지고 있습니다. 이 프로젝트의 [React 인증/인가 Best Practice](/post/frontend/react/auth-best-practice) 글에서 다룬 토큰 저장 전략 비교도 같은 맥락입니다.

---

## 큰 흐름 2 — BFF 패턴으로 토큰을 프론트엔드에서 아예 치운다

SPA/모바일 앱이 OAuth 토큰을 직접 들고 있는 대신, 백엔드(또는 BFF 계층)가 토큰을 대신 보관하고 브라우저에는 세션 쿠키만 내려주는 구조가 늘고 있습니다.

```
[SPA] ──(세션 쿠키만)── [BFF]
                          │ 실제 액세스 토큰/리프레시 토큰은
                          │ BFF가 서버 쪽에서만 보관
                          ▼
                    [Auth Provider / API]
```

브라우저에는 애초에 탈취할 토큰이 존재하지 않으므로 XSS로 토큰이 유출되는 경로 자체를 차단합니다. Auth.js, Clerk 같은 라이브러리들이 Next.js의 서버 컴포넌트/미들웨어 환경에 맞춰 이 패턴을 기본으로 지원하는 방향으로 발전해온 것도 같은 흐름입니다.

---

## 큰 흐름 3 — "직접 구현" vs "매니지드 서비스", 선택지가 뚜렷하게 갈렸다

### 매니지드 인증 서비스(Auth as a Service)

가입/로그인 화면, MFA, 소셜 로그인, 이메일 인증까지 통째로 위임하는 방식입니다.

| 서비스 | 특징 |
|---|---|
| Clerk | React/Next.js 생태계에 특화, 미리 만들어진 UI 컴포넌트 제공, 조직(Organization)/멤버십 기능 내장 |
| Supabase Auth | Supabase(Postgres 기반 BaaS)에 포함, DB의 Row Level Security와 바로 연동 |
| Auth0 / Okta | 오래된 엔터프라이즈급 CIAM, 커스터마이징 폭이 넓지만 설정도 복잡한 편 |
| WorkOS | B2B SaaS의 SSO/SCIM(기업 고객사 연동) 지원에 특화 |
| Firebase Authentication | Firebase 생태계에 포함, 모바일 앱과 궁합이 좋음 |

초기 스타트업이나 빠른 출시가 중요한 프로젝트에서 특히 선호됩니다. 인증 관련 보안 사고의 책임과 유지보수 부담을 서비스 쪽에 넘길 수 있다는 게 핵심 장점입니다.

### 셀프호스팅 오픈소스 IAM

데이터 주권이나 비용, 커스터마이징이 중요하면 직접 운영하는 선택지도 여전히 강합니다. [Keycloak](/post/backend/auth/keycloak)이 대표적이고, Ory(Kratos/Hydra)처럼 헤드리스(UI 없이 API만 제공)로 더 유연하게 조합하는 도구도 자리를 넓혀가고 있습니다.

### 프레임워크 내장형 라이브러리

애플리케이션 코드 안에 인증 로직을 직접 넣되, 저수준 구현은 라이브러리에 맡기는 절충안입니다.

| 라이브러리 | 흐름 |
|---|---|
| Auth.js(구 NextAuth.js) | Next.js 전용에서 프레임워크 어그노스틱(agnostic)으로 확장, 세션/JWT 전략을 모두 지원 |
| Lucia | 한때 "가볍고 데이터베이스를 직접 소유하는" TypeScript 인증 라이브러리로 인기를 끌었지만, 관리자가 신규 기능 개발을 중단하고 저수준 유틸리티(oslo, arctic)로 직접 구현하는 가이드 쪽으로 방향을 틀었음 |
| Better Auth | Lucia가 남긴 자리를 이어받는 흐름으로 빠르게 성장 중인 오픈소스 라이브러리, 플러그인 구조로 조직/2단계 인증 등을 확장 |

Lucia의 사례는 인증 라이브러리 생태계의 흥미로운 신호입니다. "라이브러리가 모든 걸 대신 해준다"는 전제 자체에 회의적인 시각이 있고, 대신 데이터베이스 스키마와 세션 로직을 직접 소유하되 저수준 빌딩 블록만 가져다 쓰는 방식을 선호하는 흐름이 분명히 존재합니다.

## 큰 흐름 4 — 패스워드가 사라지는 중

애플, 구글, 마이크로소프트가 함께 밀고 있는 **패스키**(Passkey, WebAuthn 기반)가 로그인 화면에 빠르게 자리 잡고 있습니다.

```
기존: 아이디 + 비밀번호 → (선택) OTP/SMS 2차 인증
패스키: 기기의 생체 인증(지문/얼굴) 또는 PIN → 공개키 기반 인증
```

비밀번호를 아예 서버에 저장하지 않으므로 유출 위험 자체가 없고, 피싱에도 훨씬 강합니다. `SimpleWebAuthn` 같은 라이브러리로 직접 붙이거나, 위에서 다룬 매니지드 서비스들이 패스키 지원을 기본 옵션으로 추가하는 추세입니다. 다만 아직은 비밀번호/소셜 로그인과 나란히 "선택 가능한 옵션" 중 하나로 제공되는 경우가 대부분이고, 완전히 대체하는 단계는 아닙니다.

---

## 정리 — 상황별로 흔히 보이는 선택

| 상황 | 흔히 보이는 선택 |
|---|---|
| 빠르게 MVP를 출시해야 함 | Clerk, Supabase Auth 같은 매니지드 서비스 |
| B2B SaaS, 기업 고객사의 SSO 연동 필요 | WorkOS, 또는 Keycloak 직접 운영 |
| 데이터 주권/커스터마이징이 중요 | Keycloak, Ory 같은 셀프호스팅 IAM |
| 직접 구현하되 저수준 도구만 원함 | Auth.js, Better Auth |
| 마이크로서비스 간 인증 | JWT 기반 스테이트리스 토큰 |
| 일반 웹 서비스의 사용자 로그인 | `HttpOnly` 쿠키 세션 + BFF 패턴 |

정답이 하나로 수렴하는 영역이 아니라, 팀 규모와 보안 요구 수준, 그리고 "어디까지 직접 책임질 것인가"에 따라 계속 갈리는 선택입니다. 다만 세션 재조명, BFF 패턴, 패스키 확산이라는 세 가지 흐름만큼은 여러 스택에서 공통적으로 나타나고 있습니다.
